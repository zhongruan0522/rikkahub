## 1. 结论摘要

- **完全死代码 / 孤儿残留（第一批零风险项已全部核验清理）**：
  - **核验修正（保留项）**：`web-ui` 中的 `@react-router/node` 与 `isbot` 虽源码无直接导入，但在无自定义 `app/entry.server.tsx` 时会被 `@react-router/dev` SPA 构建强校验，已归入第 5 节防误删清单；`app/build.gradle.kts` 的 `ExperimentalMaterial3AdaptiveApi` opt-in 仍被 `ChatPage.kt:156` 的 `currentWindowDpSize()` 依赖。
- **核心“一件事用了多个依赖且无性能提升”集中于网络、序列化与解析层**：
  1. 底层实质全走 OkHttp，但 S3 / WebDAV 另套 Ktor `HttpClient(OkHttp)` 且未复用全局 `OkHttpClient`，反而多建连接池并丢失代理、UA 和请求日志；`McpManager` 也额外自建隔离池并安装了 MCP SDK 并未使用的 `ktor-client-content-negotiation`。
  2. `:common` 已 Fork `okhttp-sse` 核心实现（`RealEventSource` / `ServerSentEventReader`），使 `okhttp-sse` 仅剩下 2 个接口。
  3. 仅为了扫描 PNG `tEXt` 字符卡元数据引入全套 `metadata-extractor` + `xmpcore`，且 EXIF 旋转同时在 `:ai`（系统 `ExifInterface`）、`:app`、`:ui`（`androidx.exifinterface`）各自实现。
  4. Ktor 传递拉入了 `kaml` + `snakeyaml-engine-kmp`，与 `:app` 显式声明的 `org.yaml:snakeyaml` 形成 YAML 解析双栈并存。
  5. `commons-text`（拉入 `commons-lang3`）全仓仅剩 2 处简单转义调用；`kotlinx-datetime` 与原生 `java.time`（`minSdk = 26` 原生可用）混用转换；`:speech` 的 12 个文件与 `SkillsVM` 仍混用 `org.json` 与 `kotlinx.serialization.json`。
- **模块边界问题突出**：`:common` 将自身不使用的 6 个库（含 `floatingx-compose`、`okhttp-logging`、`commons-text`、`kotlinx-datetime`）以 `api(...)` 泄漏给全仓下游模块，同时多个子模块重复声明上游已 `api` 导出的库。

## 3. 多依赖重叠与“大材小用”清单

### 3.1 HTTP 客户端双栈并行与连接池分裂（OkHttp vs Ktor Client）

- **底层现状**：全项目实质全部运行在 OkHttp 之上（`ai`、`common`、`search`、`mediagen`、`oauth`、`speech`、Coil 均直接使用 `OkHttpClient`；`ktor-client-okhttp` 只是在 OkHttp 之上套了一层 Ktor 客户端抽象）。
- **无收益的 Ktor Client 包装**：
  - `S3Client.kt` 与 `WebDavClient.kt`（`DataSourceModule.kt:251-264`）直接使用 Ktor `HttpClient(OkHttp)` 发起请求与文件流上传/下载，**未使用** `ContentNegotiation` 或 `SSE`，性能与能力均不优于直接复用 OkHttp。
  - 更严重的是连接池与拦截器分裂：`DataSourceModule.kt:251-264` 配置 `HttpClient(OkHttp)` 时使用 `engine { config { ... } }` 而**未传入 `preconfigured = get<OkHttpClient>()`**，导致 S3 和 WebDAV 另起一套 OkHttp 连接/线程池，且**完全绕过**全局 `SettingsProxySelector`、`SettingsProxyAuthenticator`、`User-Agent`、`Accept-Language` 与 `RequestLoggingInterceptor`。
  - `McpManager.kt:47-66` 同样自建了一个隔离的 `OkHttpClient`（也绕过代理和日志），并额外安装了 `ContentNegotiation { json(...) }`。经检查 `kotlin-sdk-client-jvm:0.15.0-rikka.4` 字节码，MCP SDK 内部的 `SseClientTransport` 和 `StreamableHttpClientTransport` 均直接使用 `McpJson` 手工编解码字符串，**从未调用 Ktor Client `ContentNegotiation`**，该插件属于无效安装。
  - `:speech` 下 12 个 TTS Provider（如 `OpenAITTSProvider.kt:24`）各自 `OkHttpClient.Builder()` 新建池，而同模块的 6 个 ASR Controller 则复用注入的共享 `OkHttpClient`。
  - `search/src/main/java/me/rerere/search/SearchService.kt:422-438` 重复实现了 `Call.await()`，而 `:search` 已依赖拥有同款 `Call.await()` 的 `:common`。

### 3.2 SSE 实现重叠：`okhttp-sse` vs 模块内 Fork

- `common/src/main/java/me/rerere/common/http/sse/RealEventSource.kt:17-20` 与 `ServerSentEventReader.kt` 已将 `okhttp-sse 5.5.0` 的内部实现拷贝到 `:common` 中以放宽 `Content-Type` 限制。
- `:ai` 的全部 5 个流式客户端与 `:common` 的 `sseFlow` 均调用自研 `me.rerere.common.http.sse.newEventSource`，`okhttp3.sse.EventSources` **0 调用**。
- 整个 `okhttp-sse` 工件目前仅用于提供 `EventSource`（2 个方法）和 `EventSourceListener`（4 个空方法）这两个极简接口。

### 3.3 HTTP 日志拦截器重叠：`okhttp-logging` vs `RequestLoggingInterceptor`

- `DataSourceModule.kt:223-228` 同时挂载了自研 `RequestLoggingInterceptor`（受用户设置开关控制并记录到应用内日志页）和 `okhttp3.logging.HttpLoggingInterceptor`（在 Debug 与 Release 构建中均无条件以 `Level.HEADERS` 输出到 logcat，仅屏蔽了 `Proxy-Authorization`）。

### 3.4 YAML 解析双栈并存：`org.yaml:snakeyaml` vs `kaml` + `snakeyaml-engine-kmp`

- 通过 `./gradlew :app:dependencies --configuration githubReleaseRuntimeClasspath` 确认：`ktor-serialization-kotlinx-json:3.6.1` → `ktor-serialization-kotlinx` → `ktor-openapi-schema:3.6.1` 已在运行时传递拉入了 `com.charleskorn.kaml:kaml:0.79.0` 与 **`it.krzeminski:snakeyaml-engine-kmp:3.1.1`**。
- 与此同时，`:app` 在 `app/build.gradle.kts:274` 又显式引入了传统 Java 版 **`org.yaml:snakeyaml:2.7`**（并在 `rikkahub.keep:17-22` 配置了 6 条 `-dontwarn java.beans.*`），全项目仅 `SkillFrontmatterParser.kt` 使用它（用于解析技能/记忆文件中的 `>-`/`|` 块与嵌套映射，并将含任意动态 key 的 frontmatter 序列化写回）。

### 3.5 图像元数据 / EXIF：3 套实现并存

- **`metadata-extractor`（+ 传递的 `com.adobe.xmp:xmpcore`）过度依赖**：全仓仅有唯一 1 个调用点——`ImageUtils.kt:240-259` 的 `getTavernCharacterMeta()`，只为了读取 PNG 的 `tEXt` chunk（检测 `[chara:` 前缀）。使用支持 JPEG/TIFF/PSD/RAW/MP4 的重量级元数据框架解析单个 PNG 文本块属于明显“大材小用”，约 25 行纯 Kotlin 读取 PNG chunk 头即可替代。
- **EXIF 旋转逻辑三处重复**：`ai/.../FileEncoder.kt:6` 使用框架自带 `android.media.ExifInterface`（`minSdk = 26`，系统 `ExifInterface(InputStream)` 从 API 24 起内置），而 `app/.../ImageUtils.kt:10` 与 `ui/.../SketchImage.kt:16` 使用 `androidx.exifinterface.media.ExifInterface`（注：`coil-core` 自身也传递依赖了 `androidx.exifinterface`），三处分别手写了旋转矩阵逻辑。

### 3.6 时间日期：`kotlinx-datetime` 与 `java.time` 混用转换

- 本项目 `minSdk = 26`，`java.time.*` 原生完整可用（`:app` 已有 100+ 处直接使用 `java.time`）。
- `:common` 声明 `api(libs.kotlinx.datetime)` 但自身 0 导入；`:ai` 自身亦在 `Message.kt`（`kotlinx.datetime.LocalDateTime`）与 `Serializer.kt` / `ServiceAccountTokenProvider.kt`（`java.time.Instant`）之间混用。
- `:app` 仅 11 个主文件导入 `kotlinx.datetime`，其中多处仅为了把 `UIMessage.createdAt` 通过 `.toJavaLocalDateTime()` / `.toJavaInstant()` 转回 `java.time` 使用。统一后可消除主业务代码对 `kotlinx-datetime` 的直接依赖（注：`coil-network-cache-control` 仍会传递带上它）。

### 3.7 JSON 解析混用：`kotlinx.serialization.json` 与 `org.json`

- 全仓以 `kotlinx.serialization.json` 为标准（240+ 文件），但 `:speech` 中仍有 **12 个 TTS/ASR 文件**（如 `OpenAITTSProvider.kt:7, 18` 同一文件内同时使用 `kotlinx.serialization.json.Json` 与 `org.json.JSONObject`）以及 `:app` 的 `SkillsVM.kt:19`、`:app:baselineprofile` 的 `MockOpenAIServer.kt:3-4` 使用 `org.json`（虽属 Android SDK 内置无体积代价，但解析风格与模型校验割裂）。

### 3.8 轻功能重依赖：`commons-text`、`:oauth` Ktor CIO、`adaptive`

- **`commons-text`（拉入 `commons-lang3`）**：全仓仅 2 处有效调用：
  1. `app/.../StringUtils.kt:27-33`：`escapeHtml()` 仅被 `Mermaid.kt:209` 调用 1 次，`unescapeHtml()` 为 0 调用（而 `oauth/.../OAuthLoopbackCallbackServer.kt:428-433` 已手写了一个 5 行 `escapeHtml()`）。
  2. `ai/.../GoogleProvider.kt:120`：`StringEscapeUtils.unescapeJson(...)` 调用 1 次。
- **`:oauth` 嵌入式 Ktor Server**：`oauth/.../OAuthLoopbackCallbackServer.kt:125-194` 仅为了监听本机 `127.0.0.1` 单路径 `GET` 回调并返回一个静态 HTML 页面，就让原本极轻量的 `:oauth` 引入了 `ktor-server-core` + `ktor-server-cio`（对比 `MockOpenAIServer.kt`，纯 `ServerSocket` 仅需数十行）。虽因 `:web` 已在 APK 中包含 Ktor Server 而暂未增加 APK 体积，但在模块层面属于过重依赖。
- **`androidx-material3-adaptive`**：全仓仅 `ChatPage.kt:156` 调用 1 次 `currentWindowDpSize()`，使用 Compose UI 内置的 `LocalWindowInfo.current.containerDpSize` 即可零依赖平替。

### 3.9 前端 `web-ui` 与 `tools/` 重叠项

- **`markdown.tsx` 重复引入且覆盖默认安全插件**：`web-ui/app/components/markdown/markdown.tsx:5-8, 114-117` 直接引入 `remark-gfm` 和 `rehype-raw` 并覆盖 `<Streamdown remarkPlugins={...} rehypePlugins={...}>`。实测 `streamdown@2.7.1` 已自带 `remark-gfm` 和 `rehype-raw`，直接覆盖不仅造成显式依赖重复，还意外顶掉了 `streamdown` 默认的 `rehype-sanitize`、`rehype-harden` 与 `codeMeta` 插件。
- **`dayjs` 与原生 `Intl` 混用**：仅在 `conversation-sidebar.tsx:145-185` 与 `conversation-search-button.tsx:51-64` 用作今天/昨天判断与 `YYYY-MM-DD` 键生成，紧接着同函数仍使用原生 `new Intl.DateTimeFormat(...)`。
- **`@tanstack/react-query` 大材小用**：全前端 `useQuery` / `useInfiniteQuery` / `useQueryClient` 均为 **0 次调用**，仅在 4 个选择器组件中调用了 7 次 `useMutation`。
- **`uuid`**：仅在 `web-ui/app/routes/conversations.tsx:56, 89, 489` 调用 2 次（注意因前端通过 Ktor 在局域网 HTTP 非安全上下文访问，不可裸用受限于 Secure Context 的 `crypto.randomUUID()`，替换时需保留 `crypto.getRandomValues` 回退）。
- **`tools/` 工具链分裂与版本漂移**：
  - `tools/i18n` 使用 `citty` CLI 框架，`tools/trace` 使用 `cac` CLI 框架；
  - 两者均基于 Bun 运行，`tools/i18n/src/config.ts:52-61` 自实现 10 行零依赖 `loadDotEnv()`，而 `tools/trace/src/index.ts:4` 额外引入了 `dotenv`；
  - `tools/i18n`、`tools/trace` 与 `web-ui` 之间在 `zod`（`4.6.7` vs `4.4.3`）、`yaml`（`2.9.1` vs `2.9.0`）、`typescript`（`7.0.2` vs `5.9.3`）、`oxfmt`（`0.74.0` vs `0.32.0`）、`@types/bun`（`1.4.3` vs `1.3.14`）上存在版本漂移。

### 4.2 其他过宽 `api(...)` 与跨模块重复声明

## 5. 经核查实际必要的依赖（防误删清单）

以下依赖虽容易在静态 grep 或直觉上被怀疑为冗余，但经核查均具有不可替代的运行时或协议作用，不可贸然删除：

1. **`sqlite-android`（fork `-SNAPSHOT`）**：`app/.../data/db/SQLiteConfiguration.kt:4-21` 与 `DatabaseUtil.kt:19` 通过它挂载 `libsimple.so` 实现 Room 中文 FTS5 分词并放宽 CursorWindow 限制。
2. **`bouncycastle-bcprov`（`:workspace`）**：源码无直接 `import`，但在运行时向 JSch 提供 Android 缺失的 Ed25519 / Curve25519 等现代 SSH 算法（且 `app/build.gradle.kts:126` 已排除 1.2 MB 的 `picnic` 查找表）。
3. **`jmdns` vs Android `NsdManager`**：`app/.../web/NsdServiceRegistrar.kt:58` 通过 `JmDNS.create(address, "rikkahub")` 广播自定义局域网域名 `rikkahub.local`。经核查 compileSdk `android.jar`，系统 `NsdManager`/`NsdServiceInfo` 不支持自定义 `.local` A 记录解析；只要保留 `http://rikkahub.local` 访问能力，就无法用 `NsdManager` 平替。
4. **`slf4j-android`**：源码无直接引用，但运行时为 Ktor、JmDNS、Pebble 提供日志实现并接入 Logcat（仅重复声明的 `slf4j-api` 可去）。
5. **`guava-listenablefuture:9999.0-empty-to-avoid-conflict-with-guava`**：空占位冲突规避包。虽不必在 `app/build.gradle.kts:204` 显式手写（因 `media3-common` 传递的 `guava:33.3.1-android` 已自动携带），但依赖解析时必须保留该防冲突机制。
6. **`@react-router/node` 与 `isbot`（`web-ui`）**：虽然 `web-ui` 源码 0 导入且启用了 `ssr: false`，但在未提供自定义 `app/entry.server.tsx` 时，`@react-router/dev` 的 `resolveEntryFiles` 在 `typegen` / `build`（SPA 预渲染 `index.html`）期间会直接检查 `web-ui/package.json` 的 `dependencies`；移除 `@react-router/node` 会报错失败，移除 `isbot` 会被 CLI 自动写回 `package.json`。
7. **`androidx-test-runner`（`:app:baselineprofile`）与 `ExperimentalMaterial3AdaptiveApi`（`:app`）**：`BaselineProfileGenerator.kt` / `StartupBenchmarks.kt` 使用的 `@LargeTest` 来自 `androidx.test:runner`（移除 `espresso-core` 后须由 `androidx-test-runner` 显式暴露到编译期）；`ChatPage.kt:156` 的 `currentWindowDpSize()` 仍属实验性 API，在替换掉 `androidx-material3-adaptive` 前不可移除对应的 `optIn`。
8. **其余经全量检索确认有真实业务调用的库**：
   - `haze` 5 件套（`ChatInputHaze.kt` 均实际调用，其中 `haze`、`haze-blur`、`haze-glass` 已由两个 `*-material3` 子包传递包含）
   - `bettertext` 4 件套（`text`、`markdown`、`latex`、`highlight` 均实际使用）
   - `androidx-ink` 5 件套（`:ui` 的 `sketch/` 均实际使用）
   - `coil-compose`、`coil-okhttp`、`coil-gif`、`coil-svg`、`coil-cache-control`（均在 `RouteActivity.kt` 实际注册并服务 SVG 图标与动态图片）
   - `androidx-media3-exoplayer`（音频与视频共用同一播放器引擎）
   - `pebble`、`diffutils`、`quickjs`、`xz`、`jsch`、`apache-sshd-*`（仅限 `:workspace` `testImplementation`）、`zxing-core` + `camera-*`、`image-viewer`、`reorderable`、`huge-icons`（跨 `:ui` 与 `:app` 145 个文件）、`androidx-paging-*`、`androidx-lifecycle-process`、`androidx-browser`、`termux-terminal-view`。
